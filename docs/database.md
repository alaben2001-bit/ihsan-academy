# تصميم قاعدة بيانات أكاديمية الإحسان — مسودة للمراجعة قبل أي تغيير

**الحالة:** مسودة تصميم فقط — لم تُنشأ جداول جديدة ولم تُنفّذ ترحيلات.
**التاريخ:** 2026-10-09
**القرار المطلوب:** اعتماد النموذج المنطقي والوجهة التقنية قبل كتابة SQL أو تغيير قاعدة الإنتاج.

## 1. القرار التقني المقترح

التطبيق الحالي هو Node.js وله طبقة تخزين تدعم PostgreSQL. تخزين PostgreSQL الحالي يعتمد سجلات JSON عامة (academy_records وacademy_meta) مع ترحيلات SQL، وليس مخططًا علائقيًا كاملًا لكل كيان.

**التوصية:** لا ننقل إلى Supabase ولا ننشئ قاعدة ثانية الآن. نثبت أولًا مصدر البيانات الفعلي ونأخذ نسخة احتياطية قابلة للاستعادة، ثم نقرر بين الإبقاء على PostgreSQL الحالي مع تحسينه تدريجيًا أو الانتقال إلى Supabase PostgreSQL بعد تجربة استعادة ومقارنة كاملة.

Supabase ليس بديلًا سحريًا عن التطبيق؛ إذا اختير لاحقًا، يجب أن يظل الخادم هو حارس الصلاحيات، وألا يوضع مفتاح الخدمة السرّي في المتصفح. ولا تُنشأ جداول أو تُنقل بيانات قبل اعتماد الخطة واختبارها على قاعدة منفصلة.

## 2. مبادئ التصميم

- حفظ حسابات الطلاب وسجلات الحضور والتقدم والدرجات والمحتوى الحالي دون فقد أو استبدال.
- فصل هوية المستخدم عن ملف الطالب أو المعلم؛ ليس كل مستخدم طالبًا.
- تطبيق أقل صلاحية، مع عزل المدرسة والفوج والطالب على مستوى الخادم.
- تخزين أوقات النظام بتوقيت UTC وعرضها حسب إعداد الأكاديمية.
- دعم العربية وRTL، وأسماء المستخدمين العربية، والبحث دون افتراض أن البريد إلزامي لكل طالب.
- استخدام معرفات ثابتة، ومفاتيح أجنبية، وقيود فريدة، وفهارس حيث يلزم.
- حفظ سجل تدقيق للعمليات الإدارية الحساسة دون تخزين كلمات مرور أو أسرار.
- التعامل بحذر مع بيانات القاصرين، مع سياسة احتفاظ وطلبات تصحيح/حذف مناسبة.
- كل تغيير بنيوي يمر عبر ترحيل مرقّم قابل للمراجعة، ونسخة احتياطية، واختبار استعادة.

## 3. النموذج المنطقي المقترح

| المجال | الجداول المقترحة | الغرض |
|---|---|---|
| الهوية والصلاحيات | users, roles, user_roles, sessions (إن احتاجها تصميم المصادقة) | حسابات الدخول والأدوار والجلسات |
| المدارس والأفواج | schools, school_staff, groups, group_memberships, teams, team_members | الهيكل التعليمي وعضوية الطالب ونطاق المعلم |
| ملفات الأشخاص | student_profiles, teacher_profiles | العمر/المستوى/الاهتمامات والبيانات التعليمية الضرورية |
| المنهج | learning_paths, courses, modules, lessons, lesson_resources | مسارات القرآن والمتون والمواد والدروس وملفاتها |
| التسجيل والتقدم | enrollments, lesson_progress, learning_plans, weekly_goals | تسجيل الطالب، وحالة الدرس، والأهداف |
| الاختبارات | question_bank, quizzes, quiz_questions, question_attempts, quiz_attempts | الأسئلة والمحاولات والنتائج والتصحيح |
| القرآن والحفظ | quran_plans, quran_sessions, quran_reviews, quran_evaluations, quran_certificates | مقدار الحفظ والمراجعة والتقييم والشهادات |
| المتابعة | attendance, attendance_weekly, grades, teacher_notes, reports, student_tasks | الحضور والدرجات والواجبات وملاحظات المعلّم |
| المشاركة | posts, media_posts, comments, reactions, discussions, notifications | منشورات وتفاعل مجتمعي مضبوط الصلاحيات |
| التحفيز | point_events, badges, student_badges, challenges, challenge_participants | سجل نقاط غير قابل للتكرار وشارات وتحديات |
| الطلبات والإدارة | group_join_requests, supervisor_requests, privacy_requests, audit_log | طلبات الانتقال والإشراف والخصوصية والتدقيق |
| التشغيل | schema_migrations, app_metrics, security_events | تتبع تغييرات المخطط والمؤشرات والأحداث الأمنية |

هذه أسماء منطقية أولية وليست أوامر SQL جاهزة. قبل التنفيذ، تُطابق مع جميع مجموعات البيانات الموجودة حاليًا لتجنب إنشاء نسخ متكررة من نفس الكيان.

## 4. العلاقات الأساسية

- المستخدم قد يمتلك دورًا أو أكثر؛ الدور وحده لا يمنح صلاحية خارج المدرسة/الفوج المصرّح به.
- ملف الطالب يرتبط بحساب المستخدم اختياريًا أثناء الاستيراد/الانتقال، ثم يُفرض الربط عندما يكون الحساب جاهزًا.
- الطالب يمكن أن ينتمي إلى فوج واحد أساسي في الوقت نفسه، مع سجل انتقالات وطلبات موافقة بدل تغيير صامت.
- المدرسة تضم موظفين وأفواجًا ومسارات؛ والمعلم لا يرى إلا النطاق المصرح به.
- المسار يضم دورات أو وحدات؛ الدورة تضم دروسًا؛ والتقدم يُسجل لكل طالب ولكل درس.
- كل محاولة اختبار ترتبط بالطالب والاختبار، وتُحفظ الإجابات والنتيجة ووقت المحاولة.
- الحضور يُسجل بتاريخ وفوج وطالب، مع قيد يمنع التكرار غير المقصود لنفس الطالب في الجلسة.
- النقاط تُسجل كأحداث مرتبطة بسبب واضح؛ لا تُمنح نقاط الإجابة الصحيحة مرارًا لنفس الإنجاز.
- الملاحظات الخاصة للمعلم لا تظهر للطالب أو غير المخولين.
- ملفات الوسائط تحفظ في تخزين ملفات خاص، بينما تخزن قاعدة البيانات بياناتها الوصفية ومسارها وصلاحيات الوصول فقط.

## 5. قواعد الأمان والخصوصية

1. لا يُقبل role أو student_id من المتصفح كدليل صلاحية؛ يُستمد المستخدم من جلسة موثوقة ويُتحقق من النطاق على الخادم.
2. إذا استُخدم Supabase، تُفعّل RLS لكل جدول مكشوف، وتُكتب سياسات تختبر المدرسة والفوج والمالك. لا يوضع service_role في الواجهة.
3. تخزين كلمات المرور يكون عبر نظام مصادقة موثوق أو تجزئة قوية؛ لا تحفظ كلمات مرور صريحة.
4. تقليل جمع بيانات القاصرين، ومنع نشر معلوماتهم أو صورهم علنًا افتراضيًا.
5. تحديد أحجام وأنواع الملفات، والتحقق من صلاحية الرفع والتنزيل، وعدم الاعتماد على إخفاء الرابط وحده.
6. نسخ احتياطية مشفرة ومحدودة الوصول، مع اختبار استعادة دوري.
7. سجل التدقيق يسجل الفعل والفاعل والوقت والمعرّف المتأثر، دون أسرار أو محتوى حساس زائد.

## 6. استراتيجية الانتقال دون فقد بيانات

**المرحلة أ — اكتشاف:** تأكيد قاعدة الإنتاج ومصدر التخزين الفعلي، وقراءة أسماء المجموعات وعدد السجلات فقط عبر اتصال مصرح به.

**المرحلة ب — حماية:** إنشاء نسخة احتياطية كاملة، والتحقق من سلامة الملف، ثم استعادته إلى قاعدة اختبار منفصلة.

**المرحلة ج — مطابقة:** بناء خريطة من كل مجموعة JSON الحالية إلى الكيان المقابل، مع حصر الحقول الإضافية والروابط والمعرّفات المتكررة.

**المرحلة د — تجربة:** ترحيل نسخة اختبار، ثم مقارنة أعداد السجلات ومجاميع التقدم والحضور والدرجات، وتجربة تسجيل الدخول والصلاحيات.

**المرحلة هـ — اعتماد:** بعد نجاح الاختبارات وموافقة صاحب الأكاديمية فقط، تُحدد نافذة الصيانة وخطة الرجوع، ثم ينفذ ترحيل الإنتاج.

لا تُحذف قاعدة قديمة ولا تُغيّر بيانات الإنتاج في أي مرحلة من مراحل المسودة.

## 7. اختبارات القبول المطلوبة قبل الإنتاج

- حساب الطالب يرى ملفه وتقدمه فقط.
- المعلم يرى طلاب أفواجه فقط، ولا يمكنه تعديل مدرسة أخرى.
- المدير يدير نطاق مدرسته وفق دوره.
- الحضور الأسبوعي يظهر في ملف الطالب بعد الحفظ وإعادة تحميل الصفحة.
- التقدم يبقى بعد تسجيل الخروج والدخول وإعادة تشغيل الخدمة.
- النقاط لا تتكرر بإعادة إرسال الطلب.
- الملفات لا تُتاح لمستخدم غير مصرح له.
- اختبار استعادة ناجح على قاعدة منفصلة.
- مقارنة قبل/بعد تثبت عدم فقد أي سجل في التحويل.
- نجاح اختبارات التطبيق وبناء الحاوية ومراجعة سجلات الأخطاء.

## 8. القرارات التي يلزم اعتمادها

1. **الوجهة التقنية:** الإبقاء على PostgreSQL الحالي مؤقتًا (الموصى به لحماية الاستمرارية) أم اعتماد Supabase بعد تجربة نقل كاملة؟
2. **المصادقة:** الإبقاء على دخول التطبيق الحالي في المرحلة الأولى أم تصميم انتقال منفصل إلى Supabase Auth؟
3. **الهيكل:** اعتماد فصل المدارس والأفواج والفرق والأدوار كما ورد أعلاه.
4. **الملفات:** تحديد ما إذا كانت ملفات الدروس عامة أم تتطلب تسجيل الدخول؛ ملفات الطلاب والملاحظات الخاصة يجب أن تبقى خاصة.
5. **النقاط والشارات:** اعتماد سجل نقاط قائم على الأحداث لمنع التلاعب والتكرار.

**لا تُنشأ أي جداول ولا يُنفذ أي SQL بناءً على هذه المسودة وحدها.**
