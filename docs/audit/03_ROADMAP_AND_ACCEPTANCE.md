# خارطة الطريق ومعايير القبول — أكاديمية الإحسان

هذه خارطة عمل مقترحة بعد المرحلة صفر. كل مرحلة تبدأ بمراجعة النطاق والبيانات الحالية، وتُنفّذ على فرع منفصل مع اختبارات. لا تُدمج تغييرات ولا تُنشر قبل مراجعة النتائج. لا يوجد في هذا المستند ادعاء بأن المراحل التالية نُفذت.

## المرحلة صفر — جرد وتوثيق (هذه المرحلة)

**النطاق:** جرد الملفات، جمع المتطلبات السابقة المتاحة، تحديد حالة المستودع، إنشاء ملفات التوثيق الأربعة.  
**ممنوع:** تعديل منطق التطبيق أو البيانات أو إعدادات الإنتاج.  
**القبول:**
- وجود ملفات التوثيق الأربعة تحت `docs/audit/`.
- الإشارة إلى مصدر المعلومات وتاريخ الجرد.
- الفصل بين الحقائق المؤكدة والفرضيات التي تحتاج اختبارًا.
- تسجيل متطلبات المستخدم دون افتراض تنفيذها.
- مراجعة المستخدم للنتائج والموافقة على بدء المرحلة التالية.

## المرحلة 1 — تثبيت خط الأساس والتدقيق الأمني

**النطاق:**
- رسم خريطة لمسارات API والوظائف والأدوار.
- تتبع التحقق من الصلاحيات في الخادم لكل مسار حساس.
- اختبار عزل المدرسة والفوج والفريق والطالب وولي الأمر.
- تدقيق الجلسات وCSRF وتحديد المحاولات وملفات تعريف الارتباط.
- اختبار المدخلات والرفع والرسائل والمرفقات وتسجيل الأخطاء.
- توحيد README ورقم الإصدار ومصدر الحقيقة للمخطط.
- مراجعة PR #13 وما إذا كانت التغييرات فيه لازمة وآمنة.

**القبول:**
- جدول API يربط المسار بالدور والنطاق واختبار السماح/الرفض.
- لا يمكن تجاوز الصلاحية بإرسال طلب مباشر.
- جميع حالات الرفض الحساسة تعيد استجابة مناسبة ولا تكشف بيانات.
- `npm test` وبناء Docker ناجحان.
- توثيق أي خطر لا يمكن إصلاحه فورًا وخطة تخفيفه.

## المرحلة 2 — سلامة البيانات والتشغيل

**النطاق:**
- تحديد التخزين المرجعي في الإنتاج.
- مراجعة ترحيلات 001–009 وترتيب تشغيلها وتكرارها.
- اختبار الكتابة بعد إعادة التشغيل وإعادة النشر.
- اختبار النسخ الاحتياطي والتحقق منه والاستعادة في بيئة منفصلة.
- توثيق خطة استعادة وتعامل مع فشل جزئي.
- التحقق من الخدمة الأساسية وإعادة توجيه الرابط القديم دون كشف أسرار.

**القبول:**
- تقرير صحة التخزين دون مشاركة بيانات أو أسرار.
- نجاح استعادة نسخة احتياطية اختبارية مع مطابقة عدد السجلات الأساسية.
- عدم وجود فقد أو تكرار في ترحيل تجريبي.
- وجود إجراء استرجاع موثق ومختبر.

## المرحلة 3 — العمود التعليمي القرآني

**النطاق:**
- ربط الطالب والمدرسة والفوج والشيخ بخطة الحفظ والمراجعة والحضور.
- تسميع الحفظ، تسجيل الأخطاء، إعادة المراجعة، وخطة يومية/أسبوعية.
- سجل رسم وضبط ومراجعة الثمن أو المقطع.
- تقارير أسبوعية وشهرية للطالب والشيخ وولي الأمر.
- تخفيف الخطة عند الحاجة دون فقد التاريخ.
- مستويات وشهادات فقط عند اكتمال معايير واضحة.

**القبول:**
- مسار كامل من طالب إلى حلقة وفوج وشيخ وخطة وحضور ومراجعة وتقرير.
- نفس بيانات الحضور والتقدم تظهر بصورة متسقة في المواضع المخولة.
- تعديل الخطة لا يمحو الإنجاز السابق.
- يستطيع الطالب معرفة الخطوة التالية دون ازدحام واجهة.

## المرحلة 4 — المنهج وبناء الطالب

**النطاق:**
- تنظيم المواد إلى أساسية وإثرائية اختيارية.
- تقسيم المحتوى إلى حفظ، مراجعة، فهم، تطبيق، قراءة ونقاش.
- بناء منهج سنوي على فصلين مع خطط شهرية وأسبوعية قابلة للتعديل.
- زيادة بنك الأسئلة مع تنوع نوعي، لا مجرد زيادة عددية.
- مراجعة المحتوى الديني ومصادره ومحتوى الصحة والمال والسلامة.
- تطبيق مراجعة متباعدة مناسبة وتوصيات مبنية على أداء الطالب.
- «رحلتي» كمسار بصري للتقدم، لا نظام نقاط سطحي.

**القبول:**
- كل درس له هدف ونوع ومصدر ومستوى وأسئلة أو نشاط مناسب.
- الأسئلة مرتبطة بالدرس والمادة، والإجابات الموضوعية فقط تصحح آليًا.
- الإجابات المفتوحة لها rubric ومراجعة معلم.
- الإضافي معلّم بوضوح كاختياري ولا يؤدي عدم إنجازه إلى وصف الطالب بالفشل.
- لا تنشر مادة شرعية غير مراجعة بوصفها حكمًا نهائيًا.

## المرحلة 5 — واجهات الأدوار والهاتف

**النطاق:**
- إعادة تنظيم واجهة الإدارة العليا على الهاتف لتبدأ بالإجراءات المهمة.
- تحسين لوحة الشيخ لتقليل خطوات الحضور والتسميع والمراجعة.
- تبسيط واجهة الطالب إلى القرآن وخطوة اليوم والرحلة والمهام.
- تبسيط واجهة ولي الأمر إلى ملخص التقدم والحضور والتنبيهات.
- توحيد RTL وحالات التحميل والخطأ والفراغ.

**القبول:**
- اختبار بصري موثق على 320/360/390/768px وسطح المكتب.
- لا يوجد تمرير أفقي غير مقصود أو تداخل للأزرار.
- يستطيع المستخدم إتمام المهام الأساسية بإبهام الهاتف وبأقل خطوات معقولة.
- التغييرات لا تكسر واجهات الأدوار الأخرى.

## المرحلة 6 — المتابعة والتواصل والمجتمع

**النطاق بعد اعتماد سياسة الخصوصية:**
- ملف تعليمي للطالب وتقارير شهرية وسنوية.
- رسائل وإشعارات ونقاشات عامة بإشراف.
- مساحة «الصراحة» المجهولة/المعروفة مع حدود سرية واضحة.
- تحديات اختيارية وزميل متابعة بموافقة الطرفين.
- استطلاع اهتمام الطلبة بدروس واختبارات مقبلة.
- الاعتذار عن الاختبار وإرفاق عذر آمن ومقيد الرؤية.
- مكتبة الشيخ والفيديوهات والصوتيات والتعليقات.
- CV الشيخ ووسائل التواصل المعتمدة.

**القبول:**
- سياسة واضحة لمن يرى كل نوع من البيانات ومدة الاحتفاظ به.
- لا يرى الطالب أو المشرف بيانات خارج نطاقه.
- لا تُكشف هوية صاحب الرسالة المجهولة للطلبة.
- آلية البلاغات والإشراف وحذف المحتوى المسيء واضحة.
- ملفات الأعذار محمية ومقيدة الوصول والحجم والنوع.

## المرحلة 7 — الميزات المالية والتطبيق

**النطاق:**
- دراسة إمكانية تبرع/إعانة CCP موثوقة بعد تحديد الجهة والملكية والمحاسبة.
- اختيار مسار التطبيق: PWA محسّن أو غلاف Android أو تطبيق أصلي، بناءً على الحاجة.
- مراجعة سياسات Google Play والخصوصية وموافقة ولي الأمر والحسابات.
- تجهيز الأيقونة ولقطات الشاشة وسياسة الخصوصية وحذف الحساب إن انطبق.

**القبول:**
- لا يوجد جمع مال قبل تحقق الجهة وآلية الاستلام والإيصال.
- ينجح التطبيق على أجهزة اختبار ونسخ Android المستهدفة.
- لا تُرفع مفاتيح سرية داخل التطبيق.
- إعدادات المتجر وسياسة البيانات متطابقة مع الوظائف الفعلية.

## بوابات الإصدار

لا يُعتبر أي إصدار مكتملًا لمجرد نجاح البناء. لكل إصدار يجب إرفاق:
1. ملخص التغيير والسبب.
2. قائمة المتطلبات التي تحققّت.
3. الاختبارات المنفذة ونتائجها.
4. اختبار قبول حقيقي للسيناريوهات الحساسة.
5. خطة تراجع/استعادة عند تغيير البيانات.
6. حدود ما لم يُختبر.
7. موافقة على الدمج والنشر عند الحاجة.

## أولويات لا تتغير

- لا نعيد بناء المشروع من الصفر.
- لا نحذف بيانات الطلبة أو نغيّر توزيعهم دون سبب موثق وموافقة مناسبة.
- لا نعتمد على إخفاء الزر بدل التحقق في الخادم.
- القرآن والتعلم الشرعي الضروريان أساس، والتوسع الإضافي اختياري.
- لا نرهق الطالب ولا نحول الدرجات إلى مقياس لقيمته.
- لا نعد بسرية مطلقة أو حماية كاملة دون تحقق.
- لا نقول إن الموقع جاهز للإنتاج قبل اختبار التشغيل الحقيقي.
