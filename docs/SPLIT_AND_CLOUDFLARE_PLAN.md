# خطة فصل المواقع والنقل — أكاديمية الإحسان في بناء الإنسان

الحالة: خطة فحص ومناقشة قبل أي تعديل بنيوي أو نقل بيانات.
الفرع: `planning/split-sites-cloudflare`.
المرجع الحرفي لأفكار المستخدم: `docs/USER_REQUIREMENTS_VERBATIM.md`.

## 1. الوجهة المطلوبة كما حددها المستخدم

1. موقع المدرسة القرآنية: مدرسة الرحمان الشيخ جابر بفوجيه، مع إضافة مدرسة الشيخ شعيب لاحقًا ومدارس أخرى مستقبلًا.
2. موقع العلم الشرعي / الإحسان في بناء الإنسان: المسارات التعليمية، المنهاج، المفاجأة الذهبية، التحديات، الاختبارات، المكتبات، الفيديوهات، رحلتي، تعلّم وارتق، والميزات الأخرى المحفوظة حرفيًا في وثيقة المتطلبات.
3. موقع تعريفي موحّد يعرّف بالأكاديمية ويربط الموقعين المستقلين.
4. دراسة نقل الاستضافة والبنية إلى Cloudflare بهدف تجنب فقدان قاعدة البيانات عند انتهاء صلاحية خدمة الاستضافة.
5. الحفاظ على رابط الموقع الحالي والبيانات أثناء مرحلة الفحص؛ لا حذف ولا تبديل DNS ولا ترحيل إنتاجي قبل بوابة قبول واضحة.

## 2. ما تمت معاينته في المستودع

- المستودع: `alaben2001-bit/ihsan-academy`، الفرع الافتراضي `main`.
- تطبيق Node.js؛ نقطة البدء `server/server.js`.
- واجهة عربية ثابتة في `index.html` و`assets/`.
- طبقة تخزين في `server/storage/`، ويظهر من التوثيق أنها تدعم JSON وSQLite وPostgreSQL بحسب الإعداد.
- قاعدة PostgreSQL على Render: `ihsan-academy-db`، منطقة Frankfurt، الخطة Free، وتاريخ الانتهاء الظاهر 2026-11-07.
- خدمة Render الأساسية الظاهرة: `ihsan-academy-frankfurt`، الرابط الحالي `https://ihsan-academy-frankfurt.onrender.com`.
- توجد وثائق سابقة في `docs/PROJECT_INVENTORY.md` و`docs/ARCHITECTURE_AND_DATA.md` و`docs/SECURITY_REVIEW.md` و`docs/CURRICULUM_BLUEPRINT.md`. وهي تصف نفسها على أنها فحص أولي وليست إثباتًا لاكتمال الاختبارات.
- أُنشئ هذا الفرع التوثيقي فقط لحفظ المتطلبات والخطة. لم تُجرَ تغييرات في كود التطبيق أو قاعدة البيانات أو إعدادات Render.

## 3. خلل مؤكد أو خطر يحتاج قرارًا

### أ. انتهاء صلاحية قاعدة البيانات
الخطة الحالية تعرض انتهاء قاعدة PostgreSQL المجانية في 7 نوفمبر 2026. يجب أخذ نسخة احتياطية فعلية والتحقق من إمكانية استعادتها في قاعدة منفصلة قبل ذلك التاريخ. وجود سكربتات النسخ في المستودع لا يثبت أن نسخة سليمة قد أُنشئت أو أن استعادتها نجحت.

### ب. Cloudflare ليس بديلًا مباشرًا لـ PostgreSQL
Cloudflare Pages وWorkers لا يقدمان قاعدة PostgreSQL مُدارة مطابقة تلقائيًا للقاعدة الحالية. خدمة D1 هي قاعدة SQL مختلفة عن PostgreSQL؛ نقل التطبيق إليها يحتاج تعديل طبقة التخزين والاختبارات. ويمكن إبقاء PostgreSQL لدى مزود يدعم قاعدة دائمة وربط التطبيق عبر بنية مناسبة، لكن ذلك لا يحقق نقل قاعدة البيانات نفسها إلى Cloudflare. يجب مقارنة التكلفة والاستمرارية والنسخ الاحتياطية قبل الاختيار.

### ج. التطبيق ليس موقعًا ثابتًا فقط
وجود خادم Node.js، وجلسات، وصلاحيات، وتخزين PostgreSQL، وعمليات رفع ملفات/نسخ احتياطية يعني أن نشر ملفات الواجهة وحدها على Pages لا ينقل وظائف التطبيق. نقل الخادم إلى Workers قد يتطلب تعديلًا لتوافق بيئة التشغيل وتخزين الملفات والجلسات وقاعدة البيانات. لا نفترض التوافق قبل فحص الاعتماد على واجهات Node وملفات النظام.

### د. ازدواجية إعدادات Render
ملف `render.yaml` يعرّف خدمتي ويب: `ihsan-academy` و`ihsan-academy-frankfurt`، مع قاعدة بيانات واحدة؛ كما يضبط الخدمة القديمة للتحويل إلى Frankfurt. هذا قد يكون مقصودًا للانتقال القديم، لكن يجب ألا ننشئ خدمات إضافية أو نغيّر Blueprint قبل مطابقة الموارد الحية والبيانات والإعدادات.

### هـ. تناقض أرقام الإصدار
ملفات التوثيق السابقة ذكرت تناقضًا بين إصدار README وعناوين الخادم و`package.json`. القراءة الحالية لـ `package.json` تظهر `65.0.0`، بينما واجهة `index.html` تستخدم أصولًا بعلامة تخزين مؤقت `v=70.0`، وسجل المستودع يتضمن تحديثًا لأصول المفاجأة الذهبية. يجب تحديد الإصدار الفعلي من commit المنشور وتوحيد التسميات حتى لا تختلط النسخة المنشورة بالنسخة التي يجري اختبارها.

### و. الأمان والجلسات
المراجعة السابقة سجلت أن الجلسات مخزنة في الذاكرة كأسئلة تحتاج اختبارًا، وأن CSRF وخصائص الكوكيز وصلاحيات الأدوار والرفع والنسخ الاحتياطية لم تُثبت جميعها باختبارات قبول حيّة. يجب حسم ذلك قبل فتح الموقعين للجمهور.

## 4. التصميم المقترح للفصل — دون فقد الميزات

- إبقاء المتطلبات الوظيفية الأصلية كاملة في الوثيقة الحرفية.
- فصل واجهات ووظائف المدرسة عن واجهات ووظائف التعليم، وعدم نسخ سجلات الطلبة إلى موقع التعليم العام بلا حاجة أو صلاحية.
- فصل الصلاحيات حسب الموقع والدور، مع إمكانية هوية موحّدة مستقبلًا إن ثبتت فائدتها؛ لا يُشترط أن يكون لكل متعلم حساب مدرسي.
- جعل موقع التعريف بوابة مستقلة خفيفة تربط الموقعين، ولا يحمل بيانات الطلبة.
- قبل فصل قواعد البيانات، تحديد البيانات المشتركة فعلًا: الحسابات، المحتوى، نتائج التعليم، سجلات المدرسة، والملفات. تُرسم علاقة البيانات ثم يُقرر هل الأنسب قاعدة واحدة مع نطاقات وصلاحيات مفصولة، أم قواعد منفصلة.
- عدم بناء نظام دخول موحّد أو نقل البيانات حتى تتحدد سياسة الحسابات للطلاب وأولياء الأمور والمعلمين.

## 5. مراحل التنفيذ وبوابات الأمان

1. **الجرد والتحقق:** فحص ملفات الخادم والتخزين والواجهات والترحيلات والاختبارات والإعدادات الحية دون كشف أسرار أو بيانات شخصية.
2. **النسخ الاحتياطي:** إنشاء نسخة مشفرة خارج الخدمة الحالية، والتحقق من سلامتها واستعادتها في بيئة معزولة.
3. **قرار الاستضافة:** مقارنة Cloudflare Pages/Workers/D1/R2 مع خيار الإبقاء على Node.js وPostgreSQL لدى مزود ذي تخزين دائم. القرار يعتمد على التوافق والتكلفة لا على الاسم فقط.
4. **خريطة الفصل:** جدول يحدد كل شاشة وAPI وجدول/مجموعة بيانات: المدرسة، التعليم، أو المشترك.
5. **تنفيذ تجريبي في فرع مستقل:** لا تغييرات على `main` أو الموقع الحي في هذه المرحلة.
6. **اختبارات القبول:** حسابات الأدوار، الحضور، حفظ القرآن، نقل الفرق، المسارات التعليمية، القلوب والنقاط، حفظ النتائج، الجلسات، النسخ والاستعادة، والهاتف.
7. **إطلاق تدريجي:** نشر الموقع التعريفي أولًا، ثم المواقع المستقلة، مع خطة رجوع واضحة ودون حذف الأصل حتى اكتمال التحقق.

## 6. معايير لا يُعلن النجاح قبل تحققها

- نسخة احتياطية قابلة للاستعادة مع تقرير نجاح.
- لا فقد في عدد السجلات ومجاميعها عند المقارنة قبل/بعد النقل.
- استمرار الحسابات والصلاحيات والبيانات بعد إعادة تشغيل الخدمة.
- عدم قدرة المستخدم على الوصول إلى بيانات مدرسة أو فوج خارج صلاحياته.
- عمل الموقعين والموقع التعريفي على الهاتف والكمبيوتر.
- اجتياز اختبارات المستودع واختبارات القبول الحي.
- بقاء رابط الموقع الحالي فعالًا حتى اعتماد الانتقال رسميًا.
